# COMMIT_RULES.en.md — Git Commit Message Conventions

Goal: readable history, machine-parseable types, stable semver signals.

## 1. Structure

```
<type>[(<scope>)][!]: <subject>

<body>

<footer(s)>
```

- subject required; scope, body, footers optional; separate sections with a blank line (the parsing boundary for `git log` / `shortlog` / `rebase`)

## 2. Subject

- ≤50 display columns, 72 the hard limit; length includes the `type(scope): ` prefix; count ASCII as 1 column, CJK characters as 2 (≈25 hanzi)
- Imperative mood: must complete "If applied, this commit will ___" (Chinese subjects: "本次提交将 ___")
- Chinese or English both fine; stay consistent within one repository
- No trailing punctuation; `!` is only a breaking-change marker (immediately before the `:`)
- Lowercase the first word of the description
- No zero-information subjects (`fix bug`, `update files`, `more fixes`)

## 3. Body

- Wrap manually at 72 columns (git never wraps automatically)
- Explain what and why, not how (the how is in the diff)
- Suggested order: problem background → the change → rationale / side effects
- `-` bullet lists allowed; omit the body when one sentence suffices

## 4. Footer

- git trailer format `token: value`; spaces inside tokens become hyphens (`Acked-by:`), `BREAKING CHANGE` is the sole exception (`BREAKING-CHANGE` is synonymous)
- issue references: `Refs: #123`, `Resolves: #45`
- breaking changes: `BREAKING CHANGE: <what broke and how to migrate>`; when `!` is used the footer may be omitted, but the description must state the break

## 5. Types

| type | meaning | semver |
|---|---|---|
| feat | new feature | MINOR |
| fix | bug fix | PATCH |
| docs | documentation | none |
| style | formatting (no semantic change) | none |
| refactor | refactoring | none |
| perf | performance | none |
| test | tests | none |
| build | build system / dependencies | none |
| ci | CI configuration | none |
| chore | maintenance | none |
| revert | reverts a commit | varies |

- Breaking change (any type): `!` before the `:` (after the scope, e.g. `feat(parser)!:`), or a `BREAKING CHANGE` footer, or both; result → MAJOR
- scope: a lowercase noun in parentheses naming a module / area; types and scopes always lowercase

## 6. Special cases

- revert: subject `revert: <original subject>`, footer `Refs: <original SHA>`. git's auto-generated default (`Revert "…"` plus a body line `This reverts commit <sha>.`) differs — rewrite by hand
- merge messages are generated by git

## 7. Examples

```
feat(parser): support nested glob patterns
```

```
fix: prevent racing of requests

Introduce a request id and an index table to track outstanding
requests. Old behavior: responses could arrive out of order and
overwrite newer data.

BREAKING CHANGE: environment variable `REQUEST_MODE` removed.
Use `concurrency.mode` in config instead.
Refs: #345
```

Counterexamples: `fixed parser bug` (past tense) / `update files` (zero information) / `feat: add feature!` (`!` is a breaking-change marker, not punctuation)

## 8. Pre-commit checklist

1. subject ≤50 display columns (≈25 hanzi, 72 the hard limit), imperative, no trailing punctuation?
2. blank line between sections?
3. body explains what and why only?
4. type, scope, and `!` breaking marker correct?
5. issue / SHA references in the footer?
